# P0 架构实验：提交路径、查询路径和重复向量存储

日期：2026-11-16。用户报告的最高正式版本是
`70b9fd50907b34c14fb44d9adea4897558f40b8e`，性能原始分 **3573.508102**；
本轮以该提交为对照，在独立分支 `minivectordb-p0-storage` 验证。
原 `minivectordb-perf5000` 分支已有其他后续修改，本轮没有回滚或覆盖它。
**本轮没有正式提测，超过 5000 仍为目标。**

结论：P0 调查有必要，但不能把已经实现的架构重复当作新优化。
三个原型没有测出稳定收益，已放弃；保留的单因素改动是索引引用不可变原行，
不再在索引中重复保存 float32 向量。它确定减少了有索引负载的文件和写 I/O，
没有证明热查询或导入耗时稳定加快。

## 1. 先还原实际架构

生产改动仅在 `minivectordb/database.cpp`，不改通信、距离计算、量化筛选、
TopK、B+ 树算法或提交同步。以下路径在 70b9 对照中已经存在：

- `main.cpp` 接收官方 JSONL，解析 SQL，再执行及输出。
- `Database::put_row` 编码原行，更新主键树；有向量索引时再更新索引树。
- `Storage::put` 使用受语句 savepoint 保护的 COW 节点；失败语句恢复两个树根。
- `Database::commit → Storage::publish` 刷脏节点，追加 catalog 和校验提交记录，
  同步数据文件后成功应答。常规提交已经是单文件、一次数据同步；
  初始化和旧格式迁移还有其他同步。
- TopK 首查扫描主键树，建立有界 int8 筛选缓存；稳定查询使用缓存中的
  行地址、量化编码及过滤位图，必要时读取原向量复核。缓存装不下的尾部仍精确扫描。
- 大 K（`LIMIT > 16384`）、无过滤、有索引时，会走索引扫描和外部排序。

所以，“将稳定查询从 B+ 树逐行扫描解耦”和“常规提交改为单文件同步”
已经部分实现。真正发现的重复工作是：索引原来额外存储 `row_offset + D × float32`，
而同一份原向量已存在不可变原行中。

## 2. 评分与负载：哪些已知，哪些未知

按用户提供的规则截图：

```text
R_X = (X_base + epsilon_X) / (X + epsilon_X)
f(R) = R / (1 + R)
E_item = 0.6 f(R_T) + 0.2 f(R_B) + 0.2 f(R_M)
E = (E_write + 2 E_query) / 3
```

综合指标中的六项权重：

| 项目 | 耗时 | I/O | 峰值内存 |
| --- | ---: | ---: | ---: |
| 写入 | 20% | 6⅔% | 6⅔% |
| 查询 | 40% | 13⅓% | 13⅓% |

这意味着查询耗时值得优先研究，但建索引、加载和预热产生的 I/O、内存不能忽略。
公式有饱和效应，不能把 `5000 / 3573.508102` 当作所需加速倍数。
组织方基线 T/B/M、平台原始分的缩放、正式索引配置尚未知；
公开驱动明确不含基线和评分器。

本轮测试采用 10000 行、128 维、1000 个不同 Top10 查询，一半带 25% 选择率过滤；
写入每批 100 行。索引是否创建是显式实验条件，不能混合两类结果。
这些是本地实验条件，不冒称正式隐藏输入。

来源：
[官方公开题包](https://github.com/oceanbase/seekdb/blob/2026-competition-round2/mysqltest/README.md)、
[官方驱动说明](https://github.com/oceanbase/seekdb/blob/2026-competition-round2/protocol_check/README.md)。
读取内容保存在 `results/p0-official-references.json`。规则页面本轮直接读取超时，
公式依据用户在本对话提供的截图，不能宣称已重新确认线上全文。

## 3. 测量条件与 A/A

- 原 Dockerfile、锁定的 GCC 14.2.0、相同编译选项。
- Apple Silicon 模拟 Linux amd64；2 CPU、128 MiB、swap=0、禁用网络。
- Linux named volume；不强制清空宿主页缓存，宿主负载没有完全隔离。
- 无埋点构建测端到端时间；独立诊断构建用于归因。
- 三个 seed：20261116、7、39034843；相邻运行，中间一轮交换顺序。
- 指标保留原始 `io.stat` 和 cgroup `memory.peak`；没有采集进程 RSS。
- 查询累计 I/O、峰值包含加载、索引准备和预热，不能说是纯查询阶段增量；
  物理设备归属和异步写回口径未经组织方认证。

同一二进制 A/A 的旧/新耗时比：

| 轮次 | 写入 | 查询 |
| --- | ---: | ---: |
| 20261116 | 0.98637 | 1.04128 |
| 7 | 1.04389 | 1.04397 |
| 39034843 | 1.01252 | 0.95763 |

同版约有 4% 波动；仅三对数据，不是统计置信区间。
后续 1%～3% 的差异不足以支持稳定提速结论。

## 4. 独立诊断：内部成本与端到端成本分开

诊断原始数据：`results/p0-diagnostic-volume.json`；
可还原插桩：`results/p0-diagnostics.diff`。
诊断未合入生产。计数器与时钟有开销，尤其是行转换和小写入计时；
这些占比用于定位，不能当作无埋点耗时预测。

### 写入

端到端 1639.979 ms，数据库内部 execute 215.065 ms。
表中阶段存在包含关系，不能全部相加：

| 内部事件 | 时间 | 相对 execute | 关系 |
| --- | ---: | ---: | --- |
| 向量数字转换 | 72.779 ms | 33.8% | 不含 JSON/SQL 解析 |
| commit | 106.433 ms | 49.5% | 包含同步、校验等 |
| fsync | 93.408 ms | 43.4% | 也含初始化；主要被 commit 包含 |
| 原行 blob 编码后的写入 | 14.140 ms | 6.6% | 包含小块写调用 |
| B+ 树 put | 5.539 ms | 2.6% | 不等于全部节点访问成本 |
| 提交校验 | 9.563 ms | 4.4% | 被 publish 包含 |

10000 次 blob、10443 次 pwrite、6428194 个逻辑写字节、105 次 fsync；
节点访问 39486 次，全部缓存命中；复制节点 entry 共 2950500 个。
这些是可识别操作数量，不是完整 malloc/复制计数。

JSON/SQL/execute/output 内部时间远小于端到端时间；
管道、Python 编解码、调度及模拟成本没有被拆开，不能把差额全部归因于数据库。
先前 host bind mount 下 blob 占比很高，而 named volume 下同步突出：
**挂载形态会改变归因，不能跨条件沿用热点结论。**

### 查询

1000 条端到端累计 738.534 ms；内部 select 148.220 ms。
首次查询端到端 14.792 ms、内部 11.431 ms；
热过滤/无过滤查询中位数分别 0.62835 / 0.76012 ms。

| 内部阶段 | 时间 | 相对 select |
| --- | ---: | ---: |
| 批量 int8 距离 | 55.898 ms | 37.71% |
| refine 整体 | 44.990 ms | 30.35% |
| 起始种子堆 | 10.281 ms | 6.94% |
| 一次缓存构建 | 8.513 ms | 5.74% |
| 表达式绑定 | 8.098 ms | 5.46% |
| 两次过滤位图构建 | 1.060 ms | 0.72% |

refine 整体包含种子复核、安全界、原行读取、float 筛选及精算；
这些子阶段未各自独立计时。查询量化、投影、排序等也未全部拆开。
没有硬件 cycles/cache miss 数据，不推测其数值。

- 有效候选 6250000；种子堆替换 58305 次。
- 整数安全界检查 6240000，拒绝 6222177，拒绝率 **99.7144%**。
- float 筛选检查 17823，拒绝 17487，拒绝率 **98.1148%**。
- 补偿精算 10336 次，其中每查询 10 个种子已贡献约 10000 次。
- 最终 TopK 替换 319 次。
- blob 读取 77823 次、逻辑读取 42326657 字节；这是逻辑访问，不是物理 I/O。
- 整轮只扫描 B+ 树一次，访问 41 个节点；稳定查询已使用缓存。

把种子堆完全消除也仅省诊断内部 select 的约 6.9%，不能据此承诺端到端同比收益。
整数界已经拒绝绝大多数候选，进一步收紧也不能消除前面的全量 int8 距离计算。
目前不替换为 `nth_element`。

原始报告 `memory_measurement` 字段误写“not collected”；
实际 `write_cgroup` / `query_cgroup` 已含 cgroup 峰值，未采集的是进程 RSS。
这里保留原始数据并勘误；复现脚本已修正文案。

## 5. 三个拒绝合入的单因素原型

所有数据、命令和二进制身份保留在 `results/p0-*-paired.json`；
可还原源差异为对应 `*-rejected.diff`。

| 原型 | 写入中位数：旧→新 | 查询中位数：旧→新 | 决定 |
| --- | ---: | ---: | --- |
| 聚合 blob 写入 | 1645.577→1651.066 ms | 557.765→559.262 ms | 无稳定收益，放弃 |
| 数据文件 fsync 改 fdatasync | 1652.554→1653.770 ms | 547.957→573.484 ms | 无写入收益，放弃 |
| 缓存原向量文件偏移 | 1653.041→1654.312 ms | 561.838→555.862 ms | 成对结果不稳定，放弃 |

偏移缓存的查询峰值中位数 21.379→23.418 MiB；
原型 ScanRow 从 16 增至 24 字节，缓存覆盖下降。
blob 聚合原型物化整条语句的行和编码，并非只有一个 1 MiB 缓冲区。
fdatasync 原型没有减少必要同步次数；目录仍使用 fsync。
这些负面结果不包装成优化成功。

## 6. 保留的单因素：索引只保存原行引用

新 posting 只有 8 字节 row offset。原行仍保存完整 float32；
原索引 inline-vector posting 也能读取，允许旧记录与新记录混合。
新格式不能保证被旧程序读取，不宣称双向兼容。

为什么保持语义：

1. 原行不可变；更新写新行，并让主键树和索引树引用同一新行。
2. 两棵树根在同一 catalog 提交发布；失败语句、回滚和恢复沿用相同边界。
3. 删除同时撤销两棵树中的可见记录。
4. 大 K 索引扫描按引用读取原向量，继续用原距离函数和排序器。
5. 没有修改 int8/float 保守界、精算、距离并列规则或 exact/ann 行为。

- 96 MiB、无 swap、40000 行、文件大于限额的提交、索引、排序、回滚及强杀恢复，

## 8. 下一步排序与边界

1. **确认正式索引配置及 T/B/M 明细。** 当前改动只有索引存在时才省去重复写，
   不能从单个原始分判断正式收益。无需更改协议或放宽 exact。
2. **有索引负载的更大表、长行、冷读复测。** 重点验证引用读取的局部性代价；
   当前 10k 结果不足以覆盖冷设备 I/O。
3. **在原生 Linux amd64 复核 int8 全扫描成本。** 内部占比最大，但 Apple 模拟下
   指令成本不代表评测 CPU；不根据本地单轮给 SIMD 下结论。
4. **提交校验与编码复制的最小原型。** 先证实真实墙钟占比，再考虑流式校验；
   不能省略自动提交确认前的持久化或减少错误检测语义。
5. **更彻底的列式布局或安全空间剪枝。** 目前没有证据支持其在该高维分布下
   获得数量级收益，迁移、回滚及超内存代价也更高，不作为已完成成果。

这轮确定的是有索引存储成本下降；性能原始分能否超过 5000，需要正式平台对新提交
给出结果。没有代提测，也没有把本地加速或 I/O 百分比换算成平台成绩。
