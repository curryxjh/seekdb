# 设计与实现边界

## 权威数据与记录布局

`/data/commit.log` 是唯一权威数据源。`LOCK` 用于 POSIX 进程排他锁，避免同一目录被两个实例同时打开。`/data/scratch/` 的哈希索引、向量索引、事务暂存及排序文件均为可重建派生数据，启动时清理并重建。重建和恢复成功之后才发出 ready。

提交帧由 `<8sQI` 头（魔数、负载字节数、CRC32）、负载和固定提交尾标组成。负载是多条 `<I length> + payload` 记录：`C` 保存 UTF-8 JSON 表定义，`I` 保存向量索引定义，`R` 保存表 ID（uint64）、主键（int64）和二进制行，`D` 保存表 ID 和删除的主键。

行中 BIGINT 为 int64，VARCHAR 为 uint32 UTF-8 字节长度及正文，VECTOR 为固定数量的 little-endian float32。VARCHAR 的限制在编码前按 Unicode 字符数验证。向量距离先按存储语义转换 float32，再使用 float64 数学计算；float32 极值相减不会在 float32 路径溢出。

每张表使用磁盘开放寻址哈希索引，槽为 `<qQ>`：主键及最新记录偏移编码，0 表示未用槽、1 表示删除、其余表示偏移加 2。SplitMix64 分散 BIGINT 键，负数与最小/最大 BIGINT 均可使用。负载率超过 0.7 时扩容，索引使用文件 mmap，由操作系统按需分页；不把所有行装入 Python 字典。

## 语句与事务原子性

SQL 先完整解析再执行，不接受把未知尾部忽略的部分解析。每条修改语句使用独立磁盘暂存层及哈希索引；任何类型、约束或重复键错误都会丢弃整层。多行插入失败不会保留前几行。

显式事务具有另一个磁盘暂存层。成功语句按顺序合并到事务层；后续读先查事务覆盖层再查已提交层，删除标记会屏蔽旧记录。语句失败不改变事务先前成功的修改。COMMIT 将整个事务层作为一个提交帧写入日志，fsync 后应用派生索引，最后返回成功。自动提交语句使用同一提交路径。ROLLBACK 丢弃事务层；关闭时也丢弃未提交层。

暂存层合并、日志写入等底层 I/O 失败视为致命错误，不继续对外提供 SQL 服务。这样不会在一个不完整日志帧后追加新的正常提交，恢复时也不会跳过半帧并误认其后的内容。

## 崩溃恢复

启动按提交顺序检查帧边界、CRC 和尾标；只有完整验证后的帧才重放。日志尾部不完整帧被截去并同步。未提交暂存目录被清理，已确认提交从日志恢复。读取和 CRC 校验分块进行，不一次载入整个事务或日志。

恢复只修改派生文件，权威日志除了丢弃不完整尾部外不被重写。因此恢复过程中再次退出后，可以从相同权威提交序列重新开始。派生表索引和磁盘向量索引都在 ready 之前恢复。进程强杀模型不包含断电、磁盘损坏、外部篡改；不宣称对这些额外故障提供修复。

## 向量索引与精确查询

`CREATE VECTOR INDEX` 建立自行实现的磁盘精确平面向量索引，内容为固定维度 float32 向量，另配主键到最新向量偏移的磁盘哈希表。创建时扫描当前可见数据，之后重放提交时同步更新向量和删除标记。事务内查询屏蔽旧版本并合并事务覆盖层；提交前不会修改已提交的向量索引。

内存足够时，一个有预算上限的表缓存保存 float64 数组与普通列，float64 精确表示已经存储的 float32。缓存预算预估为 48 MiB，并检查实际字符串占用；不是全库常驻策略。建有索引时，可在缓存中按跨度最大的维度递归中位划分，每叶约 128 条，保留叶子的轴对齐包围盒。查询以包围盒距离下界排序，维护 K 个最佳结果；下界超出当前阈值才剪枝，并保留浮点容差和主键并列规则。

普通 NumPy 精确扫描直接计算距离；有过滤时先形成满足普通列条件的候选集合。所有候选都使用实际当前记录，不预存查询答案。缓存不足时，磁盘向量索引提供精确扫描和 K 大小的候选堆；没有向量索引则从记录流计算。两种模式都是 exact，`ann` 请求也满足精确结果语义。

每次成功修改、COMMIT 或 ROLLBACK 后失效内存缓存。缓存和包围盒是加速层，不能成为事务可见性的另一份权威状态。

## 有界资源与排序

普通读按行解码。小 LIMIT 的排序使用 K 大小的堆，并根据列宽估算限制堆预算；大 LIMIT 或无 LIMIT 的排序使用预算约 8 MiB 的磁盘归并排序，最多 32 路合并，临时文件均在 `/data/scratch/`。查询 JSON 结果逐行序列化到同一物理协议行，避免在服务端同时保存完整结果集。

资源限额包含页缓存：mmap 与流式算法允许内核回收干净页面，不能把“不在 Python 堆中”理解为“不计入 cgroup 内存”。本地已设计大于 128 MiB 内存限额的数据测试；正式所有规模和 I/O 约束仍需平台验证。

## 已知限制与后续方向

- 当前提交日志为追加式，尚无 checkpoint / 日志压缩；大量重复更新会增大磁盘占用和恢复时间。
- 自研索引采用精确平面索引与可选包围盒，未实现 HNSW/IVF 等更激进的近似算法。高维数据剪枝收益可能较低；`ann` 当前不会牺牲准确率。
- 元数据保存在内存；行、向量和事务修改可在磁盘处理。超多表/列的元数据规模尚未专项压力测试。
- SQL 限于 README 列明的语法；不提供完整 MySQL 兼容性。标识符不区分大小写，比较不做语言相关排序；UPDATE 受影响行数按满足条件的行计数。
- 大数据查询的响应体仍受题包驱动最大响应字节数限制；流式输出不改变评测协议上限。
- 一次本地性能烟测不等于三轮官方端到端、cgroup I/O/内存测量，不能据此计算赛事分数。
